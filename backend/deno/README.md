# Бэкенд gotodream.ru: поиск рейсов

Deno-сервис, который принимает данные формы поиска с фронтенда, обращается за рейсами к источнику и возвращает
выдачу вместе со значениями для фильтров.

Источников два, переключаются одной переменной окружения:

| `FLIGHT_PROVIDER` | Что делает                                         | Нужна сеть |
| ----------------- | -------------------------------------------------- | ---------- |
| `mock`            | Встроенный генератор выдачи. Детерминированный.    | нет        |
| `s7`              | NDC-шлюз S7 (`agent-api/gaia`), SOAP + Basic-auth. | да         |

---

## Быстрый старт

```bash
cd backend/deno
cp .env.example .env          # заполнить S7_PASSWORD, если нужен провайдер s7
deno task dev                 # сервер на http://localhost:8000
```

Проверка, что сервер жив:

```bash
curl http://localhost:8000/api/health
# {"status":"ok","provider":"mock","time":"..."}
```

Пробный поиск без браузера:

```bash
curl -X POST http://localhost:8000/api/search \
  -H 'Content-Type: application/json' \
  -d '{"tripType":"oneWay","cabinClass":"economy",
       "itinerary":[{"origin":"DME","destination":"LED","departureDate":"2026-10-01"}],
       "passengers":{"adults":1,"teens":0,"children":0,"infants":0}}'
```

Фронтенд ходит на адрес из `REACT_APP_API_URL` (по умолчанию `http://localhost:8000`), поэтому больше ничего
настраивать не нужно.

## Подключение к шлюзу S7

Порядок ровно такой; каждый шаг отвечает на отдельный вопрос, и пропуск шага превращает следующий отказ в
загадку.

| Шаг | Команда                | На какой вопрос отвечает                        |
| --- | ---------------------- | ----------------------------------------------- |
| 1   | `cp .env.example .env` | реквизиты на месте                              |
| 2   | `deno task test`       | конверт и разбор ответа не сломаны              |
| 3   | `deno task s7:ping`    | стенд принимает запрос и отвечает предложениями |
| 4   | `deno task dev`        | HTTP-обвязка и CORS работают                    |
| 5   | `npm start` во фронте  | форма доходит до бэкенда                        |

Шаги 1–2 сети не требуют. Шаг 3 — первый, где нужен доступ к стенду: пока он не прошёл, проверять сайт
бессмысленно, отказ будет виден в браузере без причины. Обратный порядок («открыть сайт и посмотреть») — самый
долгий способ узнать, что не задан пароль.

### 1. Заполнить `.env`

```dotenv
FLIGHT_PROVIDER=s7
S7_LOGIN=go_to_dream
S7_PASSWORD=<пароль от S7>
S7_PSEUDO_CITY=S7AGN8224
S7_AGENT_USER_ID=go_to_dream
```

`.env` закрыт в `.gitignore`. Пароль в репозиторий не кладётся никогда: тестовый стенд сегодня, боевой завтра
— механика одна.

### 2. Отправить пробный запрос

```bash
deno task s7:ping                                   # DME → LED, 1 взрослый, через 30 дней
deno task s7:ping -- --from LED --to AER --adults 2
deno task s7:ping -- --from DME --to LED --date 2026-03-10 --return 2026-03-20
deno task s7:ping -- --show-request                 # показать отправляемый XML
deno task s7:ping -- --help
```

Скрипт печатает настройки, параметры, время ответа и таблицу предложений с ценой, тарифом, маршрутом, багажом
и возвратностью. Он проходит ровно тот же путь, что и сервер, поэтому «работает ping, не работает сайт» сразу
сужает поиск причины до HTTP-обвязки.

### 3. Когда что-то не сходится

```bash
S7_DUMP_DIR=./dumps deno task s7:ping
```

В `dumps/` лягут отправленный конверт и сырой ответ. Разбирать отказы NDC можно только по исходному XML:
содержательная причина живёт в теле ответа, а не в HTTP-статусе.

### 4. Работа без доступа к стенду

```bash
S7_FIXTURE=search/providers/s7/fixtures/airshopping-rs-ow-adt.xml \
FLIGHT_PROVIDER=s7 deno task dev
```

Сеть не используется вообще: транспорт отдаёт сохранённый ответ стенда. Режим нужен, когда стенд недоступен, а
фронт разрабатывать надо.

## Устройство

```
main.ts                     точка входа, список маршрутизаторов
search/
  config.ts                 вся конфигурация из переменных окружения
  schema.ts                 контракт запроса (zod), повторяет frontend/.../contract.js
  offer.ts                  типы выдачи: Offer, Leg, Segment — граница системы
  reference.ts              справочники аэропортов и авиакомпаний
  filters.ts                фильтры, сортировка, фасеты
  handler.ts                HTTP: разбор, проверка, вызов провайдера, ответ
  providers/
    types.ts                интерфейс FlightProvider и коды отказов
    registry.ts             выбор провайдера по конфигурации
    cache.ts                кэш выдачи + объединение одинаковых запросов
    mock.ts                 генератор
    s7/
      request.ts            SearchRequest -> XML AirShoppingRQ
      transport.ts          SOAP-вызов: auth, таймауты, повторы, дампы
      xml.ts                разбор XML и безопасный доступ к узлам
      parse.ts              AirShoppingRS -> Offer[]
      provider.ts           сборка трёх слоёв
      fixtures/             настоящие ответы стенда, на них гоняются тесты
tools/
  s7_ping.ts                пробный запрос из командной строки
testing/
  assert.ts                 утверждения для тестов, без внешних зависимостей
```

### Почему слоёв столько

Каждый слой проверяется отдельно и без сети. Построитель конверта проверяется сравнением с рабочим примером,
парсер — на сохранённых ответах стенда, транспорт — единственное место, где вообще есть `fetch`. Когда шлюз
ответит не так, как ожидалось, чинить придётся один файл, а не «всё, что связано с S7».

### Почему фильтры не уходят в запрос к шлюзу

Страница перезапрашивает выдачу при каждом движении фильтра (`useFlightSearch`). Для генератора это бесплатно,
для NDC-шлюза — секунды и квота. Поэтому у поставщика спрашивают только то, что меняет ответ (маршрут,
пассажиры, класс, валюта), результат кладётся в кэш на 5 минут, а фильтры и сортировка применяются локально
поверх него. Ключ кэша фильтры не включает — иначе кэш не попадал бы ни разу.

## Формат ответа

```jsonc
{
  "searchId": "…",
  "flights": [{
    "id": "s7-OF1-2026-07-03-S7-2511",
    "offerId": "OF1",              // идентификатор предложения у S7
    "price": 15553, "currency": "RUB",
    "cabinClass": "economy",       // economy | comfort | business
    "fareBrand": "BASIC ECONOMY",  // бренд тарифа внутри кабины
    "bookingClass": "Q",
    "seatsLeft": 9,
    "from": "Москва", "to": "Иркутск",
    "date": "2026-07-03", "departureTime": "21:10", "arrivalTime": "13:10",
    "durationMinutes": 720, "duration": "12 ч", "stops": 1,
    "legs": [ /* по одному на направление, внутри segments — сами рейсы */ ],
    "baggage": { "carryOn": "10KG", "checkedIncluded": false },
    "priceBreakdown": { "base": 14300, "taxes": 1253, "taxDetails": [ … ] },
    "refundable": false
  }],
  "facets": { "airlines": […], "cabinClasses": […] },
  "meta": {
    "total": 12, "totalBeforeFilters": 36,
    "source": "s7", "warnings": [], "elapsedMs": 1840
  }
}
```

Обязательные поля совпадают с тем, что уже рисует `FlightList.jsx`. Всё остальное — необязательное: провайдер
заполняет, что умеет, интерфейс показывает, что пришло.

### Ошибки

```jsonc
{ "error": { "code": "PROVIDER_TIMEOUT", "message": "Шлюз S7 не ответил вовремя", "details": [] } }
```

| Код                      | HTTP | Что произошло                           |
| ------------------------ | ---- | --------------------------------------- |
| `VALIDATION_ERROR`       | 422  | Параметры формы не прошли проверку      |
| `PROVIDER_MISCONFIGURED` | 500  | Не заданы переменные окружения для s7   |
| `PROVIDER_AUTH`          | 502  | Шлюз отклонил логин/пароль              |
| `PROVIDER_TIMEOUT`       | 504  | Шлюз не ответил за `S7_TIMEOUT_MS`      |
| `PROVIDER_UNAVAILABLE`   | 502  | Сеть, 5xx или SOAP Fault                |
| `PROVIDER_BAD_RESPONSE`  | 502  | Ответ пришёл, но разобрать не удалось   |
| `PROVIDER_REJECTED`      | 422  | Шлюз осмысленно отказал (блок `Errors`) |

Ответ «200 OK» с блоком `Errors` внутри — это отказ, а не пустая выдача. Молча показать «ничего не найдено» на
неверный запрос значит спрятать ошибку.

## Что осталось непроверенным на живом стенде

Из контейнера, где собирался код, адрес `qa-gaia.s7.ru` недоступен, поэтому всё ниже — обоснованные решения, а
не подтверждённые факты. Каждое проверяется одним запуском `deno task s7:ping` с доступом к стенду.

1. **Сам факт связи.** Конверт совпадает с рабочим примером из тестового окружения структурно и по порядку
   блоков, но ни разу не отправлялся.
2. **Заголовки.** `SOAPAction` отправляется в кавычках (`"http://api.s7.ru/…"`) — так требует SOAP 1.1 и так
   он выглядит в примерах обмена. Имя операции берётся из WSDL с заглавной буквы (`SearchFlightsJourney`),
   хотя в одном примере из документации встречается строчная (`http://api.s7.ru/book`). Шлюзы на CXF обычно
   маршрутизируют по корневому элементу тела и заголовок игнорируют; если окажется иначе, имя операции
   меняется переменной `S7_OPERATION`, а `X-API-Version` включается переменной `S7_API_VERSION=0.52`.
3. **Подростки 12–18.** Отправляются как `ADT`. Если S7 поддерживает отдельный PTC (`YTH`), он задаётся
   параметром `teenPTC` в `request.ts`.
4. **Группировка пассажиров.** Отправляется `<PTC Quantity="2">ADT</PTC>`. В примерах S7 всегда был один
   пассажир каждого типа, так что вариант «несколько отдельных `Traveler`» не исключён; переключается
   параметром `travelersStyle`.
5. **Класс обслуживания.** В запрос не передаётся: соответствие «эконом/комфорт/бизнес» кодам PADIS 9873 на
   стороне S7 не подтверждено. Класс отбирается по ответу. Включается `S7_SEND_CABIN_PREFERENCE=true`, коды
   правятся в `CABIN_CODE`.
6. **Комфорт-класс.** В ответах стенда встречались только кабины `Y` и `B`. Если S7 продаёт премиальный
   эконом, его код нужно добавить в `mapCabinClass`.
7. **Дробные суммы.** В метаданных ответа указано `Decimals=2`, но все суммы приходят целыми рублями и
   трактуются как рубли, а не копейки. При работе с валютами, где это не так, проверить в первую очередь.
8. **Сложный маршрут (`complex`).** Схема его допускает, на стенде такой сценарий не проверялся.

Схему запроса можно проверить формально, но только с доступом к стенду: XSD отдаёт сам шлюз, в архив они не
входят.

```bash
curl -u go_to_dream:PASSWORD \
  "https://qa-gaia.s7.ru/agent-api/wsdl?xsd=AirShoppingRQ.xsd" > AirShoppingRQ.xsd
S7_DUMP_DIR=./dumps deno task s7:ping
xmllint --noout --schema AirShoppingRQ.xsd dumps/<время>-request.xml
```

(XSD в каталоге `refund&queue&…` из архива для этого не годятся: это IATA 2019.1 с другим пространством имён,
они описывают послепродажные операции, а не поиск.)

## Что дальше: бронирование

Поиск — первый из четырёх шагов сценария S7 (`searchFlightsJourney` → `reprice` → `book` → `demandTickets`).
Два факта из разбора архива, которые влияют на устройство следующего шага, стоит знать заранее.

**`OfferID` не идентификатор.** В ответе он уникален только внутри своей группы `AirlineOffers`, а групп
несколько: в сценарии «туда-обратно» их четыре по три предложения, и `OF1` встречается в каждой. Поэтому ключ
карточки собирается из `OfferID` и полного маршрута, а не из одного `OfferID`.

**Reprice не ссылается на предложение.** `ItinReshopRQ` из архива не содержит `OfferID` вообще: он заново
перечисляет рейсы (`SegmentKey`, аэропорты, даты, времена, перевозчики), а к каждому сегменту —
`FareBasisCode` и `RBD`, плюс список пассажиров с `ObjectKey`. Значит, для перехода к бронированию в
предложении надо хранить эти поля **по каждому сегменту**, а не одно значение на предложение, как сейчас
(`bookingClass`, `fareBasis` берутся с первого сегмента). В ответах стенда все сегменты одного предложения
имеют один тариф, поэтому сегодня это не видно — и сломается на первом же маршруте, где тарифы сегментов
различаются.
